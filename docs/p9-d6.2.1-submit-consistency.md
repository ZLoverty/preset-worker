# P9-D6.2.1 — Submit-Time Consistency Enrichment

## Result

Formal Submit now regenerates `consistency_report` from the attachments and
Preset artifact processed during the current Submit operation. Preview remains
unchanged, and approval/publication do not invoke consistency generation.

## Actual Submit call path

```text
WorkerRuntime.run_once()
  -> _discover("VALIDATING", action="enrich")
  -> _dispatch(..., action="enrich")
  -> SubmissionEnrichment.enrich_submission()
  -> _enrich_submission_timed()
  -> process_candidate()
  -> build_consistency_report()
  -> update_submission(..., consistency_report=...)
```

`CandidateResult.source_artifact` is passed directly to
`build_consistency_report()`. The native Preset is not downloaded a second
time. The first `preset 3mf` attachment is selected using the existing
attachment semantics, and is downloaded once by the consistency builder.

## Behavior

- Six canonical slicers use the existing validator dispatch.
- Valid Preset + 3MF writes a fresh `READY` report.
- Missing 3MF explicitly writes an empty report.
- Invalid 3MF or validator exceptions write the existing sanitized `ERROR`
  envelope while preserving successful native enrichment.
- Native validation/candidate failure explicitly clears the old report.
- Report-field write failures retry with a sanitized `ERROR`, then explicitly
  clear the field if necessary. Unrelated write failures are re-raised.
- The formal result is written together with canonical JSON, native diff,
  validation, version data, and the existing `READY_FOR_REVIEW` status.
