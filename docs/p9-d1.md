# P9-D1 — Shared Consistency Engine & Slot-Aware Comparison

## Background

The Preset Management System currently implements P9-B2 consistency validation for BambuStudio.

P9-C and P9-D0 established that:

- BambuStudio, OrcaSlicer, SnapmakerOrcaSlicer, CrealityPrint, and ElegooSlicer use Bambu-style 3MF project configuration structures.
- These projects store the eight P9 parameters under `Metadata/project_settings.config`.
- PrusaSlicer uses `Metadata/Slic3r_PE.config` with an INI-style representation.
- The current BambuStudio validator couples project extraction, Preset normalization, filament identity matching, slot selection, and comparison.
- Real fixtures demonstrate that project parameter arrays may contain multiple filament slots while an exported Preset contains only one value.
- OrcaSlicer fixtures contain duplicate exact filament identities at slots 1 and 4, with identical values for all eight target parameters.
- PrusaSlicer can establish identity from the Preset filename stem when it uniquely matches a project profile name.

P9-D1 will extract the reusable stored-value comparison logic and implement reliable slot-aware parameter selection.

**This is a core implementation and isolated testing phase. It must not enable new slicers in production Preview.**

---

## Objectives

1. Separate generic comparison logic from BambuStudio-specific parsing.
2. Introduce an explicit representation of project filament slots.
3. Compare Preset values against the selected project slot rather than entire project arrays.
4. Support deterministic handling of duplicate filament identities.
5. Preserve existing P9-B2 report semantics and backward compatibility.
6. Validate the shared engine against real fixtures from P9-D0.
7. Establish a minimal interface for future slicer-specific adapters.

Avoid creating a general-purpose slicer plugin framework.

## D1.2 — Introduce a Minimal Shared Comparison Core

Create a small reusable module under the existing `three_mf` package.

Suggested conceptual responsibilities:

```text
Shared Consistency Core
├── canonical parameter values
├── project slot selection
├── slot-aware value extraction
├── numeric/string normalization
├── parameter comparison
└── comparison result generation
```

The shared core must not:

- Instantiate `BambuStudioProcessor`.
- Read 3MF ZIP members directly.
- Assume a specific slicer identifier.
- Depend on Feishu or Preview services.
- Resolve slicer-specific inheritance.
- Interpret printer-specific G-code.
- Infer runtime-effective settings.

The shared core should receive already-extracted, slicer-normalized values and explicit identity evidence.

Prefer small typed data structures over nested untyped dictionaries where they improve clarity.

Reuse existing report structures wherever possible.

Do not introduce unnecessary abstraction layers.

## D1.3 — Canonical Parameter Representation

Continue using the eight existing P9 parameters:

```python
TARGET_PARAMETERS = (
    "filament_flow_ratio",
    "filament_max_volumetric_speed",
    "nozzle_temperature",
    "nozzle_temperature_initial_layer",
    "fan_min_speed",
    "fan_max_speed",
    "fan_cooling_layer_time",
    "slow_down_layer_time",
)
```

The shared core should distinguish:

- A parameter absent from the Preset.
- A parameter absent from the project.
- A scalar value.
- A one-element array.
- A filament-slot-indexed array.
- A malformed or ambiguous array.
- A value whose semantic mapping is unresolved.

Do not infer that every array is indexed by filament slot.

Slot indexing must be established by the extraction adapter or explicit parameter metadata.

Preserve original stored values for provenance.

Normalization must not destroy evidence about source types, units, or indices.

## D1.4 — Filament Identity and Slot Selection

Implement a reusable slot-selection mechanism.

Inputs should include:

- Preset identity candidates.
- Project filament identities.
- Project slot indices.
- Identity matching strategy.
- Canonical project parameter values.
- Evidence describing the origin of the identity.

Do not use parameter equality alone to establish filament identity.

### Case A — Exactly one matching slot

Select the matching slot.

Status:

`UNIQUE`

### Case B — Multiple exact identity matches with equivalent target values

For example:

```text
Preset identity: L2002CF @BBL P2S

Slot 1: L2002CF @BBL P2S
Slot 2: Other Preset
Slot 3: Another Preset
Slot 4: L2002CF @BBL P2S
```

If every target parameter that can be reliably extracted for the matching slots has equivalent stored values, and no unresolved parameter could invalidate that equivalence, allow deterministic selection of the lowest matching slot.

Record:

- All matching slot IDs.
- Selected slot ID.
- Identity evidence.
- Verified parameter equivalence.
- Any limitations.

Use an internal reason such as:

`MULTIPLE_EQUIVALENT`

Do not introduce a new externally visible report status unless required by the existing schema.

### Case C — Multiple exact matches with different or unresolved values

Return:

`AMBIGUOUS`

Do not arbitrarily choose the first matching slot.

### Case D — No matching identity

Return:

`UNRESOLVED`

Do not infer identity from parameter equality.

### Case E — Filename-based identity

Allow filename-stem identity only when a slicer-specific adapter explicitly enables it.

The filename stem must exactly match a project-side profile identity.

If exactly one project slot matches, identity may be resolved.

If multiple slots match, apply the same equivalence rules as Case B.

Do not enable filename fallback globally for Bambu-style JSON Presets.

### Indexing

Use a clearly documented internal slot-index convention.

Prefer zero-based indices internally and convert to the existing report's slot numbering only at the reporting boundary.

Do not change the meaning of existing public `slot_id` fields.

## D1.5 — Slot-Aware Parameter Extraction

Implement slot-aware extraction before value comparison.

Example:

```text
Project:
  filament_settings_id = ["A", "B", "C", "D"]
  nozzle_temperature   = ["230", "220", "225", "230"]

Preset:
  filament_settings_id = ["A"]
  nozzle_temperature   = ["230"]

Matching slots: 1 and 4
```

Both matching project slots contain `230`, so the parameter is equivalent for this fixture.

The shared engine should compare the Preset's value against the selected project slot value.

It must not compare the Preset's single-element array against the entire four-element project array.

However:

- Do not index scalar parameters as arrays.
- Do not assume all one-element arrays are global defaults.
- Do not silently broadcast arrays.
- Do not truncate mismatched arrays.
- Do not select an array element when slot association is unproven.
- Do not treat an absent parameter as a matching value.

If a parameter cannot be safely associated with the selected slot, preserve an unresolved or not-comparable outcome.

### Multiple matching slots

For each target parameter:

1. Determine whether the parameter is slot-indexed.
2. Extract the values at all matching slots.
3. Normalize values using established parameter semantics.
4. Compare those values for equivalence.
5. Mark the parameter ambiguous if values differ.
6. Preserve unresolved status when the array interpretation is uncertain.

A duplicate identity must not silently hide project-level overrides.

## D1.6 — Shared Value Comparison

Move reusable stored-value comparison logic out of Bambu-specific code.

Support existing statuses:

- MATCH
- MISMATCH
- MISSING_IN_PRESET
- MISSING_IN_3MF
- UNRESOLVED
- AMBIGUOUS
- NOT_COMPARABLE
- NOT_APPLICABLE

Preserve existing numeric comparison behavior and tolerances unless a demonstrated bug requires a change.

Do not introduce slicer-specific parameter aliases into the shared comparison core.

Adapters must map native parameter names into canonical parameter identifiers before comparison.

Preserve element-level reporting where the existing schema requires it.

For slot-selected scalar comparisons, ensure that `comparison_rows` clearly identifies the selected source slot and original array index without creating misleading extra rows for unrelated project slots.

## Acceptance Criteria

P9-D1 is complete when:

1. The shared comparison core no longer depends on BambuStudio-specific parsing.
2. The BambuStudio validator delegates reusable comparison logic to the shared core.
3. Verified slot-aware comparisons select the appropriate project parameter value.
4. Duplicate exact identities are handled deterministically only when equivalence is established.
5. Ambiguous or unresolved slot mappings do not produce misleading MATCH results.
6. Existing BambuStudio single-slot behavior remains compatible.
7. Existing P9-B2 report structure remains compatible.
8. Real P9-D0 fixtures are exercised in isolated tests.
9. Negative cases have explicit test coverage.
10. Production Preview behavior is unchanged.
11. All relevant tests pass.
