# P9-D5 — Cross-Slicer Preview Integration Audit & Production Enablement Plan

## Mission

Conduct a comprehensive, evidence-based, read-only audit of the P9 consistency validation system across all six supported slicers.

Produce a concrete, implementation-ready plan for enabling cross-slicer consistency validation in production Preview during P9-D6.

**P9-D5 is an audit and planning phase, not an implementation phase.**

Do not modify production code, Preview routing, Feishu schema, Miaoda, approval behavior, or publication behavior.

The outcome must be a verified integration contract, a risk assessment, and an executable P9-D6 implementation plan.

---

## 1. Background

The Preset Management System currently supports six slicers:

1. BambuStudio
2. CrealityPrint
3. ElegooSlicer
4. OrcaSlicer
5. SnapmakerOrcaSlicer
6. PrusaSlicer

The previous P9 stages established the following components.

### P9-B2 — BambuStudio

Implemented BambuStudio 3MF–Preset consistency validation and connected it to production Preview.

The report uses:

`p9b2.consistency.v1`

The Feishu Submission table stores the result in a single multiline field:

`consistency_report`

The stored envelope is conceptually:

```json
{
  "status": "READY",
  "generated_at": "...",
  "report": {}
}
```

Error states use the existing ERROR representation.

Preview consistency validation is informational and non-blocking.

### P9-D1 — Shared Comparison Core

Introduced:

`comparison_core.py`

It provides:

- Stored-value comparison.
- Numeric normalization.
- Filament identity and slot selection.
- Duplicate identity equivalence handling.
- Comparison statuses.
- Parameter-level provenance.

### P9-D2 — CrealityPrint and ElegooSlicer

Implemented:

- `validate_creality_consistency(...)`
- `validate_elegoo_consistency(...)`

Both reuse native Preset processors, shared project extraction, the comparison core, and shared report orchestration.

### P9-D3 — OrcaSlicer and SnapmakerOrcaSlicer

Implemented:

- `validate_orca_consistency(...)`
- `validate_snapmaker_orca_consistency(...)`

The real Orca fixture has duplicate equivalent identity matches at slots 1 and 4.

The real Snapmaker fixture has a unique match at slot 1.

### P9-D4 — PrusaSlicer

Implemented:

`validate_prusa_slicer_consistency(...)`

PrusaSlicer uses a dedicated project parser for:

`Metadata/Slic3r_PE.config`

Its filename-based identity matching is explicitly limited to PrusaSlicer.

### Current production state

Only BambuStudio consistency validation is enabled in production Preview.

The other five validators are independently callable but not connected to Preview dispatch.

The full test suite previously contained a known unrelated baseline failure:

```text
tests/test_diff_contract.py

Expected: IMPORTANT_PARAMETER
Actual: OTHER_PARAMETER
```

Verify the current status rather than assuming it remains unchanged.

## 7. D5.5 — Concurrency and Stale-Result Risk Audit

This is a critical part of P9-D5.

The Worker polls Feishu and may process Preview requests while users edit Submission records.

Investigate whether a Preview result can become stale between:

1. Reading the Submission.
2. Downloading attachments.
3. Running validation.
4. Writing `consistency_report`.

### Example race

```text
T0: Worker reads Preset A + Project X

T1: Worker begins consistency validation

T2: User replaces Project X with Project Y

T3: Worker finishes validation of A + X

T4: Worker writes READY report for A + X

T5: UI displays stale result while Y is attached
```

Determine whether existing mechanisms prevent this.

Inspect:

- Submission version or revision fields.
- Attachment identifiers.
- Input fingerprints.
- Preview request identifiers.
- Status transition guards.
- Idempotency logic.
- Retry behavior.
- Concurrent Worker behavior.
- Feishu update semantics.

Do not assume a transaction or compare-and-swap capability exists.

### Evaluate mitigation strategies

Compare at least:

**A. Input fingerprint recheck**

Re-read relevant Submission fields before writeback and compare against the inputs used for validation.

**B. Preview request generation identifier**

Associate each Preview request with a generation or request ID.

**C. Conditional write / optimistic concurrency**

Use only if the actual Feishu API and repository support it.

**D. Existing state-machine guard**

Reuse an existing protection if it genuinely prevents stale writes.

Evaluate each option for:

- Correctness.
- Required schema changes.
- Complexity.
- Multiple Worker safety.
- Residual race windows.
- Retry compatibility.

Explicitly distinguish a best-effort pre-write recheck from an atomic stale-write guarantee.

Recommend a concrete strategy for P9-D6.

Do not implement it in P9-D5.

- A consistency ERROR report.

- A primary Preview failure.

Document the decision rules.

Recommend isolated exception handling where needed.
