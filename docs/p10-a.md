# P10-A — Preset Worker Slicer Architecture Audit

## Role

You are a senior Python software architect auditing the existing `preset-worker` repository.

Your task is to establish an accurate, code-grounded baseline for adding support for new 3D-printing slicers.

This audit will be used to develop a reusable Coding Agent Skill named `slicer-onboarding`.

**This phase is strictly audit-only. Do not modify production code, tests, configuration, or existing documentation.**

You may create the requested audit report under `docs/`.

Do not implement a new slicer or create the Skill yet.

---

## 1. Objectives

Investigate the current architecture and determine:

1. How slicers are identified and dispatched.
2. How Native Preset files are parsed and normalized.
3. How Preset inheritance is handled.
4. How canonical artifacts are generated.
5. How Native Preset Diff and Validation work.
6. How 3MF files are parsed.
7. How 3MF parameters are mapped to canonical parameters.
8. How Native Preset–3MF consistency is evaluated.
9. How slicer-specific components are registered.
10. How fixtures and regression tests are organized.
11. Which steps are required to onboard a new slicer.
12. Which onboarding steps can be automated by a Coding Agent.

The final output must be actionable enough that a separate implementation phase can build a reliable onboarding Skill without rediscovering the architecture.

Do not rely on previous audit reports as authoritative evidence. Verify the current repository implementation.

## 9. Consistency Validator Architecture

This section is a high priority.

Trace the complete path:

```text
3MF raw data
    |
    v
Slicer-specific extraction
    |
    v
Parameter resolution
    |
    v
Filament / slot selection
    |
    v
Canonical parameter mapping
    |
    v
Native Preset value resolution
    |
    v
Value normalization
    |
    v
Comparison
    |
    v
Consistency Report
```

Verify the actual order and implementation.

For each stage, identify:

- Input and output structures.
- Function and module.
- Failure conditions.
- Diagnostics.
- Slicer-specific behavior.
- Tests.

### Status semantics

Inspect the actual report contract for statuses such as:

- `MATCH`
- `MISMATCH`
- `MISSING_IN_PRESET`
- `MISSING_IN_3MF`
- `UNRESOLVED`
- `AMBIGUOUS`
- `NOT_COMPARABLE`
- `NOT_APPLICABLE`

Use the exact implemented status vocabulary.

For every status, document:

1. Definition.
2. Code path producing it.
3. Required evidence.
4. Whether it represents a genuine data limitation.
5. Whether it can indicate missing implementation coverage.
6. Whether a reason code or diagnostic is provided.

### Critical investigation: extracted parameters becoming UNRESOLVED

Determine whether the following scenario is possible:

1. The 3MF extractor successfully obtains a parameter.
2. The extracted parameter is visible in intermediate data.
3. The Consistency Validator emits `UNRESOLVED` for that parameter.

If possible, identify all code paths that produce this result.

Investigate:

- Missing parameter mappings.
- Alias mismatches.
- Unsupported value shapes.
- Unresolved inheritance.
- Filament slot ambiguity.
- Array-index ambiguity.
- Missing comparison rules.
- Type conversion failures.
- Missing Native Preset values.
- Extractor output not consumed by the comparator.
- Exceptions converted into generic unresolved statuses.

Distinguish:

**A. Correctly unresolved:** The available evidence genuinely cannot determine a value.

**B. Coverage gap:** The data exists, but the relevant extraction or mapping implementation is missing.

**C. Implementation defect:** The data and mapping exist, but the validator fails to use them correctly.

Do not automatically treat all `UNRESOLVED` results as bugs.

Identify whether the current report provides sufficient diagnostics to distinguish these cases.

### Important-parameter coverage

Determine whether every Native Diff `IMPORTANT_PARAMETER` is represented in the Consistency Report.

For each important parameter, inspect:

- Canonical identity.
- Native Preset mapping.
- 3MF extraction mapping.
- Comparison implementation.
- Fallback status when unsupported.
- Diagnostic reason.

Report any important parameters that are silently omitted.

Do not invent 3MF extraction capabilities that are not implemented.

## 13. Automation Opportunities

Evaluate which onboarding tasks can be reliably automated from fixtures.

Examples:

- Detecting file format.
- Listing JSON/INI keys.
- Inspecting ZIP entries.
- Identifying candidate inheritance fields.
- Discovering candidate parameter mappings.
- Generating fixture inventories.
- Generating parser smoke tests.
- Generating comparison test skeletons.
- Checking registration completeness.
- Running regression tests.
- Generating compatibility reports.

Distinguish:

**Deterministic automation:** Safe to perform without user confirmation.

**Evidence-based inference:** Agent may propose a mapping, but must validate it against fixtures.

**Requires user confirmation:** Semantic details that cannot be reliably inferred.

Examples requiring possible confirmation:

- Meaning of multi-element arrays.
- Filament-slot indexing.
- Plate selection semantics.
- Printer compatibility syntax.
- Whether two similarly named parameters are semantically equivalent.
- Whether a field is a slicer-specific system field or a printing parameter.

The Skill must never invent these semantics.
