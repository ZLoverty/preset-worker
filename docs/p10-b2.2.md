## 5. Canonical parameter identity model


Adapt the location if the current architecture suggests a better fit.

The catalog should represent:

- Human-readable description.

- Importance classification.

For example, a conceptual definition could be:

```python
ParameterDefinition(

    description="Nozzle temperature",
```

This is illustrative, not a mandatory API.

Choose the simplest representation that satisfies the actual code.

### Requirements

- Aliases must be explicit.
- The catalog must be inspectable by tests and onboarding tooling.
- It must support slicer-specific fields.
- It must support indexed array paths where appropriate.
- It must not require changing Native Preset storage formats.
- It must not add canonical IDs to serialized Native Diff rows.

Avoid a complex schema framework.

Avoid excessive class hierarchies.

## 6. Important distinction: identity versus importance

The catalog must distinguish parameter identity from Diff classification.

A parameter may have:

- A stable canonical identity.
- Multiple native aliases.
- Slicer-specific path representations.
- An importance classification.

Do not assume that every important parameter is comparable through 3MF.

The following are separate concerns:

**Native Diff importance**

Determines whether a changed native field is classified as `IMPORTANT_PARAMETER`.

**Consistency coverage**

Determines whether a parameter can be extracted, resolved, mapped, and compared between Native Preset and 3MF.

P10-B2.2 must centralize the first concern.

It must only inventory the second concern.

Do not modify Consistency behavior based on the new catalog in this phase.

## 7. Native path matching

Implement path matching appropriate to the current Diff flattener output.

Inspect the actual path representation before choosing an algorithm.

The matcher must handle the relevant forms, potentially including:

```text
nozzle_temperature
nozzle_temperature[0]
filament_retraction_length
filament_retraction_length[1]
```

Use the real repository conventions, not these examples as assumptions.

### Required properties

1. Exact scalar paths match correctly.
2. Approved indexed-array paths match correctly.
3. Unknown paths do not accidentally match.
4. Prefix collisions are prevented.
5. Slicer-specific aliases do not leak into other slicers.
6. Matching is deterministic.
7. Native Diff paths remain unchanged.

Do not implement broad fuzzy matching.

Do not use substring-based classification.

For indexed arrays, recognize the path shape without assuming the semantic meaning of each array element.

The catalog's ability to classify an indexed field does not establish that the field can be compared with a specific 3MF slot.
