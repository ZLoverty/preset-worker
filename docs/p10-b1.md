## 6. SKILL.md Requirements

The entry-point Skill must contain:

### 6.1 Purpose

Explain that this Skill is used when:

- Adding support for a new slicer.
- Assessing whether a slicer can reuse an existing processor.
- Extending Native Preset support.
- Extending 3MF extraction support.
- Extending consistency comparison support.
- Evaluating supplied fixtures for a new slicer.

It must not activate for unrelated Worker development.

### 6.2 Inputs

Define the expected user inputs:

**Required for full onboarding**

- Target slicer name.
- Target slicer version.
- Native Preset fixture.
- Target repository.

**Required when claiming 3MF support**

- Real 3MF fixture.
- Evidence linking the 3MF to the corresponding Native Preset.
- Expected parameter values or an explicit characterization step.

**Conditional**

- Parent presets.
- Multi-filament fixtures.
- Multi-plate fixtures.
- Printer model.
- Filament identity.
- Official or built-in presets.
- Supported slicer aliases.
- Feishu slicer labels.
- Version metadata repository.

Do not require all optional inputs before starting discovery.

### 6.3 Operating modes

Define three modes:

**DISCOVERY**

Inspect repository and fixtures.

Produce an onboarding assessment.

No production code modifications.

**IMPLEMENTATION**

Implement approved adapters, registrations, and tests.

Allowed only after the necessary semantic questions are resolved.

**VERIFICATION**

Run acceptance checks and produce a capability report.

Do not introduce unrelated features or refactors.

If the user does not specify a mode, default to DISCOVERY.

A request to implement a slicer may authorize the implementation phase, but the Agent must still stop when required semantic evidence is missing.

### 6.4 Core workflow

Define the required sequence:

1. Inspect current repository.
2. Inspect processor and consistency registries.
3. Characterize fixtures.
4. Identify format family.
5. Identify reusable components.
6. Build a capability gap assessment.
7. Propose parameter mappings.
8. Resolve semantic uncertainty.
9. Implement approved changes.
10. Run targeted tests.
11. Run cross-slicer regression tests.
12. Produce the final acceptance report.

Do not skip the discovery and semantic verification stages.

### 6.5 Guardrails

The Skill must explicitly forbid:

- Guessing undocumented parameter semantics.
- Assuming all JSON-based slicers are Orca-compatible.
- Assuming 3MF files share the same internal structure.
- Selecting the first filament slot without evidence.
- Flattening arrays without confirmed index semantics.
- Treating missing parameters as matches.
- Treating unsupported parameters as matches.
- Claiming inherited values are resolved when inheritance is only preserved.
- Claiming complete consistency coverage based on a few successful comparisons.
- Changing unrelated slicers to make onboarding tests pass.
- Silently modifying shared comparison contracts.
- Claiming runtime-effective values without supporting evidence.

- Candidate parameter fields.
- Identity fields.
- Inheritance references.
- Parameter array shapes.
- Filament slots.
- Plate and object metadata.

### 9.4 Semantic confirmation

- Array-index meaning.

- Plate selection.
- Parent inheritance rules.
- Printer compatibility rules.
- Unit conversions.
- Parameter aliases.

## 10. Capability Declaration

Define a mandatory capability declaration for every onboarding attempt.

Use the following dimensions:

| Capability | Allowed declaration |
|---|---|
| Native Preset | Supported / Unsupported |
| Validation | Supported / Unsupported |
| Diff | Supported / Unsupported |
| 3MF Extraction | Supported / Partial / Unsupported |
| Consistency | Supported / Partial / Unsupported |
| Inheritance Resolution | Supported / Preserve Only / Unsupported |
| Multi-filament | Supported / Partial / Unsupported |
| Multi-plate | Supported / Partial / Unsupported |
| Publication | Verified / Not Verified |

This is an onboarding report contract, not a new Worker runtime API.

Do not modify Feishu schemas or production data models.

### Declaration rules

**Supported**

The capability has implemented behavior, suitable fixtures, and passing relevant tests.

**Partial**

The supported subset is explicitly defined, tested, and documented.

**Unsupported**

No reliable implementation is available or the required evidence is insufficient.

**Preserve Only**

Inheritance metadata is retained without resolving effective inherited values.

**Verified**

The publication path has been exercised with relevant integration tests.

**Not Verified**

Publication behavior has not been demonstrated.

Never infer `Supported` merely because a parser returns without raising an exception.

Each capability must include:

- Evidence.
- Relevant fixtures.
- Tests.
- Known limitations.

## 12. Important-Parameter Coverage Procedure

Document how the future Agent must assess important-parameter coverage.

The P10-A audit identified multiple parameter catalogs:

- Processor-local important-parameter sets.
- `three_mf/comparison_core.py` parameter definitions.
- `three_mf/consistency.py` required comparison parameters.
- Prusa-specific comparison targets.

Verify their current locations.

The Skill must require a parameter coverage matrix with at least:

| Canonical parameter | Native source | 3MF source | Selection rule | Comparison support | Evidence |
|---|---|---|---|---|---|

For every important Native Preset parameter, determine whether:

- It is extracted from the Native Preset.
- It is available in the 3MF.
- Its values can be mapped reliably.
- Slot/array semantics are established.
- It is included in consistency comparison.
- It is intentionally unsupported.

Do not require all important parameters to be comparable.

Instead, require explicit disclosure of unsupported coverage.

### UNRESOLVED guardrail

The Skill must distinguish:

**Legitimate unresolved**

Insufficient evidence to select or normalize a value.

**Coverage gap**

The data exists but the extractor, mapping, or comparator does not cover it.

**Implementation defect**

The required mapping and evidence exist, but the implementation produces an incorrect result.

A successful 3MF extraction is not proof that consistency comparison is complete.

The Agent must test representative parameters through the entire extraction-to-comparison pipeline.

Do not change parameter catalogs during P10-B1.

## 16. Human Decision Checkpoints

The Skill must define explicit stop conditions.

### Stop before implementation when:

- Native format is not understood.
- Required fixture is missing.
- Slicer identity is ambiguous.
- Canonical naming requirements conflict.
- Parameter alias semantics are uncertain.
- Array or slot semantics are unknown and required for the requested capability.
- Inheritance behavior would require unverified assumptions.
- Unit conversion cannot be justified.
- Existing shared contracts would need modification without approval.

### Stop before acceptance when:

- Registration is incomplete.
- Required tests fail.
- A new regression is detected.
- Claimed consistency parameters are not actually compared.
- Capability declaration lacks evidence.
- Publication is claimed verified without a suitable test.

The Agent may continue implementing independent, well-understood capabilities when another capability is blocked.

It must report partial completion accurately.

- Inspect current registries.
