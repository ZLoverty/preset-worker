# P10-D1 — Worker–Miaoda Diff/Consistency Data Contract Audit

## Role

You are a senior software engineer auditing the integration between two repositories:

1. `preset-worker` — generates Native Preset Diff, Validation, and 3MF Consistency reports.
2. Miaoda frontend — parses these reports and renders the merged parameter comparison table.

This is a **read-only, evidence-driven, cross-repository audit**.

Do not modify production code, tests, schemas, or fixtures during P10-D1.

The goal is to identify the exact root cause of incorrect or incomplete Native Diff ↔ 3MF Consistency row association and propose the smallest reliable correction.

## 1. Observed problem

The current Miaoda interface displays a table with columns:

- Parameter
- Original Preset
- New Preset
- 3MF
- Consistency

It groups rows into:

- Important parameters
- Other parameters
- System and metadata
- 3MF-only consistency comparisons (no Preset change)

The observed output contains examples such as:

| Native Diff parameter | Native new value | Consistency parameter | 3MF value | UI result |
|---|---:|---|---|---|
| `nozzle_temperature[0]` | 290 | `nozzle_temperature` | 290 | Separate rows |
| `nozzle_temperature_initial_layer[0]` | 290 | `nozzle_temperature_initial_layer` | 290 | Separate rows |
| `fan_max_speed[0]` | 10 | `fan_max_speed` | 10 | Separate rows |
| `fan_cooling_layer_time[0]` | 31 | `fan_cooling_layer_time` | 31 | Separate rows |
| `pressure_advance[0]` | 0.08 | No visible counterpart | — | Not checked |
| `textured_plate_temp[0]` | 50 | No visible counterpart | — | Not checked |

The 3MF-only group also contains array values, for example:

```json
["1", "1", "1", "1"]
```

Some such rows are displayed as missing, even though the 3MF column contains a value.

These are observations from the rendered UI, not yet verified Worker JSON facts.

Do not assume that removing `[0]` produces a valid match.

Do not assume a Native Preset array index corresponds to a 3MF filament slot.

Do not assume a displayed missing status is incorrect without inspecting the original comparison status and operands.

## 2. Audit objectives

Answer the following questions with source and runtime evidence.

1. Does Worker output enough information to associate Native Diff rows with Consistency rows reliably?
2. Does Worker use different parameter identities or paths in the two reports?
3. Are canonical parameter IDs from the P10-B2.2 catalog exposed in either report?
4. Does the Consistency report preserve the native source path, selected filament slot, and comparison operands?
5. Does Miaoda ignore available association information?
6. Does Miaoda perform string-based matching that fails for indexed native paths?
7. Are some rows legitimately unmatched because they represent different parameters, different slots, or unsupported comparisons?
8. Are the displayed statuses faithful to Worker output?
9. Which repository should own each part of the correction?
10. Can the issue be corrected without breaking historical reports or existing Feishu records?

The audit must distinguish data-contract defects, frontend association defects, and genuine Consistency coverage limitations.

## 7. Parameter identity and array semantics

Investigate whether the current data contract distinguishes:

1. Canonical parameter identity.
2. Native field path.
3. Native array element index.
4. 3MF parameter source path.
5. 3MF filament slot index.
6. Selected filament identity.

These are not necessarily equivalent.

For example:

```text
Native: nozzle_temperature[0]
Consistency: nozzle_temperature
```

The two rows may refer to the same conceptual parameter, but their actual comparison relationship depends on the Native Preset format and 3MF selection semantics.

Inspect the source code and fixtures to establish whether the relationship is valid for the observed slicer.

Do not globally strip numeric indexes.

Do not match by suffix, prefix, or substring alone.

Do not collapse multiple distinct Native rows into one Consistency row.

Do not infer identity solely from equal numeric values.

### Multi-filament considerations

Assess:

- Single-filament 3MF.
- Multiple filament slots.
- Repeated identical parameter values.
- Ambiguous identity.
- Missing identity.
- Different slot ordering.
- Multiple Native indexed values.

Determine which cases can be safely associated and which must remain separate.

## 9. Root-cause classification

For every observed issue, classify the root cause as one or more of:

### WORKER_CONTRACT_GAP

Worker internally knows the relationship but does not serialize sufficient association metadata.

### WORKER_MAPPING_DEFECT

Worker extracts or maps a parameter incorrectly.

### WORKER_SELECTION_LIMITATION

The identity or slot cannot be resolved reliably from the supplied artifacts.

### MIAODA_ASSOCIATION_DEFECT

Worker supplies sufficient information, but Miaoda fails to associate the rows correctly.

### MIAODA_PRESENTATION_DEFECT

Rows are correctly associated, but labels, values, grouping, or statuses are displayed incorrectly.

### CONSISTENCY_COVERAGE_GAP

The parameter is important for Native Diff but is not part of the current Consistency target set.

### INSUFFICIENT_EVIDENCE

Available data cannot establish the root cause.

Provide source and fixture evidence for every classification.

Multiple classifications may apply to one parameter.

## 10. Proposed target contract

After establishing the actual root cause, propose a minimal backward-compatible association contract.

Evaluate whether the following concepts are needed:

- `parameter_id`
- `native_path`
- `native_index`
- `slot_index`
- `filament_identity`
- `association_status`
- `association_reason`

These are candidate concepts, not mandatory field names.

Do not add all of them automatically.

Prefer reusing existing serialized fields when sufficient.

If introducing `parameter_id`, verify that the P10-B2.2 catalog can provide a stable identity for both Native Diff and Consistency rows.

If the Consistency target name does not map unambiguously to a canonical parameter ID, report the ambiguity.

Do not create a second independent parameter catalog in Miaoda.

### Backward compatibility

Consider:

- Existing Feishu records without new fields.
- Historical Diff reports.
- Historical Consistency reports.
- Optional diagnostics introduced in P10-B2.3.
- Current report schema versions.
- Current frontend rendering behavior.

Propose a safe fallback for old reports.

Unknown association must remain explicitly unverified rather than being forced into a match.
