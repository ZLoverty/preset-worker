# P9-D6.2.1 — Submit-Time Consistency Enrichment

## Objective

Extend the existing formal Submission enrichment workflow to regenerate the 3MF–Preset consistency report when an engineer submits a Preset for review.

The consistency report must be computed from the attachments processed during the **current Submit operation**, independently of any previous Preview.

Reuse the existing P9-D6.1 consistency implementation.

This is a narrowly scoped backend integration task, not a new validation phase or architectural redesign.

## 1. Background

The Worker currently supports six slicers through:

`src/preset_worker/services/consistency_preview.py`

The shared entry point is:

`build_consistency_report()`

Supported slicers:

- `BambuStudio`
- `CrealityPrint`
- `ElegooSlicer`
- `OrcaSlicer`
- `SnapmakerOrcaSlicer`
- `PrusaSlicer`

P9-D6.1 integrated consistency validation into Preview.

P9-D6.2 implemented a unified comparison table in Miaoda that reads the existing Feishu Submission field:

`consistency_report`

However, the formal Submit workflow already performs native Preset enrichment and Diff generation, but does not regenerate the consistency report.

This creates a correctness gap:

1. Engineer runs Preview with Preset A and 3MF A.
2. Worker writes a READY consistency report.
3. Engineer replaces 3MF A with 3MF B.
4. Engineer submits without another Preview.
5. Formal enrichment regenerates native Preset data, but the consistency report still describes 3MF A.

The reviewer may therefore see a report that does not correspond to the submitted artifacts.

The goal is to close this gap without changing the existing Preview design.

---

## 2. Authoritative Lifecycle Contract

Consistency validation runs on two explicit events:

- Preview requested.
- Formal Submit enrichment executed.

It does not run automatically when attachments or other fields are edited.

| Event | Required behavior |
|---|---|
| Upload or replace attachments without Preview or Submit | Preserve existing report |
| Preview with valid Preset and 3MF | Regenerate READY |
| Submit with valid Preset and 3MF | Regenerate READY |
| Submit without 3MF | Clear report |
| Submit with invalid 3MF | Write sanitized ERROR |
| Submit with native Preset processing failure | Clear previous report |
| Submit with validator exception | Write sanitized ERROR, preserving successful native enrichment |
| Submit after earlier Preview | Ignore previous report and recompute |
| Approval or publication | Do not regenerate |

The formal Submit result is the authoritative consistency snapshot for the review stage.

Do not reuse a previous Preview report as the formal Submit result.

Do not require Preview to have been executed before Submit.

## 5. Formal Submit Result Semantics

### 5.1 Valid Preset + valid 3MF

Generate a fresh READY envelope:

```json
{
  "status": "READY",
  "generated_at": "UTC ISO timestamp",
  "report": {
    "schema_version": "p9b2.consistency.v1"
  }
}
```

The real `report` must contain the full validator output.

Write it to the existing Feishu field:

`consistency_report`

### 5.2 Valid Preset + no 3MF

Explicitly write:

```python
"consistency_report": ""
```

Do not omit the field from the formal enrichment payload.

Otherwise, a previous Preview report may remain.

### 5.3 Valid Preset + invalid 3MF

Generate the existing sanitized ERROR envelope.

Native Preset enrichment should still succeed.

Consistency validation is informational and must not independently reject the Submission.

### 5.4 Validator exception

Use the existing error isolation in `build_consistency_report()`.

Do not expose raw exception details, stack traces, credentials, or attachment content to the Feishu report.

Write an ERROR envelope without changing the native enrichment result.

### 5.5 Native Preset enrichment failure

Clear the previous consistency report as part of the formal Submit failure handling.

Preserve the existing native failure status and error behavior.

Do not generate a new READY consistency report if the native Preset could not be processed.

### 5.6 Unsupported slicer

Preserve the existing formal enrichment behavior for unsupported slicers.

Ensure that a previous consistency report is not carried forward as a successful current result.

Do not silently route the slicer through another validator.

## 6. Integrate Into Formal Feishu Writeback

Locate the existing writeback for successful formal enrichment.

Include the newly generated `consistency_report` in the same logical result update as the native enrichment outputs wherever the current architecture permits.

Preserve:

- Canonical JSON.
- Native Diff.
- Existing validation messages.
- Base version information.
- Current version information.
- Submission status transitions.
- Existing reviewer metadata.
- Existing error handling.

Do not introduce a separate background writeback operation unless required by the current implementation.

### Report write failure

Reuse the established D6.1 behavior:

1. Attempt to write the generated report.
2. If the report field itself causes a write failure, retry with a small sanitized ERROR envelope.
3. If that fails, explicitly clear the report.
4. Do not silently omit `consistency_report` and leave an older READY report.
5. Do not treat unrelated Feishu API failures as consistency-field failures.

Avoid unbounded retries.

### Formal enrichment and consistency isolation

A consistency validator failure must not block otherwise successful native enrichment.

However, do not claim that the formal report was successfully refreshed if every attempt to replace or clear the old field fails.

Use the existing logging and error reporting mechanisms to expose that persistence failure.

Do not invent a new Submission status.

## 7. Preserve Preview Behavior

P9-D6.1 must remain unchanged in observable behavior.

- Recomputes consistency.
- Writes READY, ERROR, or empty.
- Preserves the Draft workflow.
- Does not trigger formal review submission.

- Runs the existing formal native enrichment.

- Enters the existing review workflow according to current native enrichment rules.

Do not combine Preview and Submit state transitions.

If a small shared helper can eliminate duplicated consistency writeback handling, it is acceptable.

However, do not create a general-purpose workflow abstraction merely for this change.
