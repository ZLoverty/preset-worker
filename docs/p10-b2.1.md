# P10-B2.1 — Slicer Registration Completeness Guard

## Role and objective

You are a senior Python engineer working in the `preset-worker` repository.

Implement a minimal, reliable guard against incomplete slicer registration.

The current architecture has two independent registration mechanisms:

- Native Preset processors, primarily composed through `slicers/registry.py`.
- 3MF Consistency validators, dispatched through `services/consistency_preview.py`.

A slicer may be registered for Native Preset processing while its consistency validator is missing. This can cause consistency processing to be skipped without a sufficiently explicit indication of unsupported capability.

**The goal is to make this condition detectable, testable, and non-silent without redesigning the existing architecture.**

This phase must remain narrowly scoped.

## 2. Required behavior

The system must distinguish these cases:

| Case | Native processor | Consistency validator | Required behavior |
|---|---|---|---|
| A | Registered | Registered | Normal processing |
| B | Registered | Missing, explicitly unsupported | Native processing remains available; consistency is clearly unsupported |
| C | Registered | Missing, expected supported | Configuration/integration defect; must not be silently accepted |
| D | Missing | Registered | Orphan validator; must be detected |
| E | Missing | Missing | Unknown slicer; preserve existing unsupported-slicer behavior |

The implementation must distinguish **intentional lack of consistency support** from **accidental missing registration**.

Do not assume every slicer must support 3MF consistency.

Do not introduce a rule that blocks Native Preset processing solely because consistency is unsupported.

---

## 3. Design constraints

Prefer a small registration/capability validation mechanism over a new registry framework.

Keep the existing processor registry and consistency validator dispatch unless a narrowly scoped adjustment is necessary.

Do not:

- Introduce a generic plugin framework.
- Rewrite `SlicerProcessor`.
- Move all validators into processor classes.
- Refactor 3MF parsers.
- Change parameter mappings.
- Change comparison status semantics.
- Modify the eight-parameter consistency target set.
- Change Diff classification.
- Add Feishu fields.
- Change publication schemas.
- Add runtime dependencies.

Use existing abstractions and naming conventions where possible.

Avoid introducing a second, independently maintained list of supported slicers that can drift from both registries.

A capability declaration is acceptable only if it has a clear purpose and is checked against actual registration.

## 5. Define explicit consistency capability

Implement the smallest appropriate mechanism to distinguish:

- `SUPPORTED`: A validator is expected and must be registered.
- `UNSUPPORTED`: No validator is expected; this is intentional.

These labels are conceptual. Adapt them to existing project conventions if needed.

A declaration may be derived from an existing authoritative source or implemented as a small explicit capability mapping.

If introducing a mapping, enforce these invariants:

1. Every registered Native Processor has a capability declaration.
2. Every declared `SUPPORTED` slicer has a registered validator.
3. Every declared `UNSUPPORTED` slicer does not silently acquire a validator without updating the declaration.
4. Every registered validator belongs to a registered Native Processor.
5. Duplicate or conflicting declarations are rejected.
6. Canonical IDs are used consistently.

Do not add a broad feature matrix to production runtime solely for this task.

The full capability matrix remains an onboarding/reporting artifact defined by the P10-B1 Skill.

## 6. Registration completeness checker

Implement a small reusable validation function.

It should inspect the actual registered processors, actual consistency validators, and explicit capability declarations.

The function should identify:

- Missing processor capability declaration.
- Missing expected validator.
- Orphan validator.
- Unexpected validator for an explicitly unsupported slicer.
- Unknown capability declaration.
- Duplicate/conflicting canonical identities where detectable.

Prefer structured, deterministic diagnostics.

For example, a checker may return an ordered collection of issues containing:

- Issue code.
- Canonical slicer ID.
- Human-readable explanation.

The exact type and API should follow existing repository conventions.

Avoid complex configuration objects or unnecessary class hierarchies.

The checker must not rely on hardcoded assumptions that there are exactly six slicers.

Adding a seventh slicer must naturally participate in validation.

---

## 7. Enforcement strategy

Implement two layers of protection.

### 7.1 Automated registration tests

Add tests that verify the completeness checker against the default production composition.

These tests must fail when:

- A processor is added without a capability declaration.
- A slicer is declared `SUPPORTED` without a validator.
- A validator is registered without a processor.
- A validator exists for an explicitly `UNSUPPORTED` slicer.

Use synthetic registry inputs to test invalid combinations.

Do not mutate global production registries during tests.

### 7.2 Runtime dispatch protection

Inspect `build_consistency_report()` and its callers.

Ensure that a slicer whose consistency capability is declared `SUPPORTED` cannot silently return an empty or apparently successful report because its validator is missing.

Use the existing error/reporting mechanism where possible.

Preserve the existing handling of:

- No 3MF attachment.
- Explicitly unsupported consistency capability.
- Invalid Native Preset.
- Invalid 3MF.
- Validator execution failures.

**Do not conflate a missing validator with a missing 3MF attachment.**

A missing expected validator is an internal configuration error, not a user artifact error.

Prefer localized enforcement at the consistency dispatch boundary.

Do not add expensive registry validation to every record-processing step.

If startup validation is feasible using the existing runtime initialization, evaluate it. Implement startup failure only if it does not unintentionally block legitimate Native Preset-only processing or introduce undesirable deployment behavior.

At minimum, the dispatch boundary and automated tests must protect against silent partial registration.

---

## 8. Error semantics

For a missing expected validator:

- Return or raise a deterministic internal configuration diagnostic.
- Preserve enough information to identify the slicer.
- Do not return `{}` as though consistency were not requested.
- Do not classify the problem as malformed user 3MF data.
- Do not fabricate comparison rows.
- Do not report `MATCH`.
- Do not report `UNRESOLVED` merely to hide missing implementation.

If the current Feishu consistency envelope can represent this condition using existing error fields, use it.

Do not introduce a new report schema version unless absolutely required.

If the existing envelope cannot distinguish this failure without a schema change, document the limitation and choose the smallest backward-compatible behavior.

For explicitly unsupported consistency capability, preserve informational behavior and make unsupported status clear to the caller.

Do not change the meaning of the existing `UNRESOLVED` comparison status.

## 9. Test requirements

Add focused tests for the following cases.

### 9.1 Valid composition

- All current production slicers pass completeness validation.
- Aliases resolve to canonical IDs.
- Each declared supported slicer has a validator.
- The checker returns deterministic results.

### 9.2 Missing declaration

Construct a synthetic processor registry containing an additional slicer without a capability declaration.

Expected: completeness check reports the missing declaration.

### 9.3 Missing expected validator

Declare a synthetic slicer as `SUPPORTED`, but omit its validator.

Expected:

- Completeness check fails.
- Dispatch does not silently return an empty report.
- Error identifies the missing validator and canonical slicer ID.

### 9.4 Explicitly unsupported consistency

Declare a synthetic slicer as `UNSUPPORTED` with no validator.

Expected:

- Completeness check passes for this capability.
- Native processing remains permitted.
- Consistency is not incorrectly claimed as supported.

### 9.5 Orphan validator

Register a synthetic validator without a matching processor.

Expected: completeness check reports the orphan validator.

### 9.6 Conflicting registration

Declare a slicer `UNSUPPORTED` while a validator exists.

Expected: completeness check reports a conflict.

### 9.7 Unknown slicer

Use an identifier not present in the processor registry.

Expected: existing unsupported-slicer behavior remains intact.

### 9.8 Missing 3MF

Use a registered slicer with a supported validator but no 3MF attachment.

Expected: existing missing-attachment behavior remains unchanged.

### 9.9 Existing integration behavior

Verify that:

- Preview continues to process valid Native Presets.
- Formal Submit continues to process valid Native Presets.
- Publication behavior is unchanged.
- Existing registered validators remain reachable.
- Existing aliases remain functional.

Use mocks or existing test fixtures where appropriate.

Avoid dependence on unavailable external fixture files for the focused registration tests.
