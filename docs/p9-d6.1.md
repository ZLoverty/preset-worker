# P9-D6.1 — Cross-Slicer Preview Integration

## Objective

Enable all six existing 3MF–Preset consistency validators in the production Preview workflow.

Reuse the existing Preview architecture, native Preset processors, Feishu `consistency_report` field, report envelope, and exception handling.

Fix the known stale-report retention defects that occur when a **new Preview is executed**.

Keep the implementation small and focused.

**Important product contract: Consistency validation is executed only when the user requests Preview. The report is a snapshot of that Preview, not a continuously synchronized representation of the current Submission.**

Do not introduce concurrency-control infrastructure, automatic invalidation, or new Feishu fields.

## 2. Product Semantics — Preview Snapshot

The following behavior is authoritative for P9-D6.1.

### 2.1 Outside Preview

These operations must not automatically recompute, clear, or invalidate `consistency_report`:

- Uploading a new 3MF.
- Replacing an existing 3MF.
- Uploading or replacing the native Preset.
- Changing the slicer.
- Editing other Submission fields.

The previous report may remain visible until Preview is requested again.

This is intentional, not a stale-data defect.

The existing `generated_at` value identifies when the report was generated.

Do not implement watchers, background reconciliation, or automatic attachment-change detection.

### 2.2 During a requested Preview

| Preview outcome | Required `consistency_report` behavior |
|---|---|
| Valid Preset + valid 3MF | Replace with new READY envelope |
| Valid Preset + no 3MF | Clear to empty string |
| Valid Preset + malformed/invalid 3MF | Replace with ERROR envelope |
| Native Preset validation failure | Clear to empty string |
| Unsupported slicer causing native Preview failure | Clear to empty string |
| Consistency validator raises an exception | Write sanitized ERROR envelope; preserve native Preview success |
| Repeated Preview | Recompute and replace the previous result |
| Report cannot be stored and fallback is triggered | Clear or replace with a small ERROR envelope; never leave an old report |

All behavior above applies only when the Worker processes a Preview request.

### 2.3 Preview input snapshot

Use the inputs obtained through the existing Preview processing path.

Do not re-read Submission attachments immediately before writeback.

Do not reject a Preview result merely because the user edited the Submission while it was being processed.

The report represents the inputs processed by that Preview execution.

Do not claim atomic consistency with the latest Submission state.

## 7. D6.1-E — Fix Field Write Fallback

Inspect:

`_write_preview_result()`

The existing fallback for a Feishu consistency-field size/write error can remove `consistency_report` from the retry payload.

This may preserve a previous report.

Change the fallback so that a completed Preview never silently leaves the previous consistency report intact when consistency report storage fails.

Preferred behavior:

1. Attempt the normal Preview write.
2. If the error is specifically attributable to storing `consistency_report`, use the existing bounded fallback mechanism.
3. Retry with a small sanitized ERROR envelope, if supported.
4. If the ERROR envelope itself cannot be stored, explicitly clear `consistency_report` with an empty string.
5. Preserve the native Preview result wherever the existing API behavior permits.

Do not indiscriminately retry unrelated Feishu failures as consistency-field failures.

If Feishu rejects every write involving `consistency_report`, including an empty string, do not silently omit the field and report success as though the old report were cleared.

Instead, surface an explicit write failure through the existing error handling/logging mechanism.

Avoid unbounded retries.

Do not introduce a new persistence layer.

## 8. D6.1-F — Preserve Non-Blocking Validation

Consistency validation is informational.

It must not:

- Reject a valid native Preset.
- Prevent successful native Preview.
- Change canonical JSON.
- Change UnifiedDiff.
- Change approval eligibility.
- Change publication behavior.
- Change PresetVersion creation.
- Change the existing Submission state machine.

Preserve the existing consistency exception boundary.

A consistency validation failure should affect only the consistency report.

Do not modify the six validators' comparison logic unless a concrete integration defect requires a narrowly scoped fix.

Document any such fix and add a regression test.
