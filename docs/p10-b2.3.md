## 4. Establish a diagnostic taxonomy

The existing report uses comparison statuses such as:

- `MATCH`
- `MISMATCH`
- `MISSING_IN_PRESET`
- `MISSING_IN_3MF`
- `UNRESOLVED`
- `AMBIGUOUS`
- `NOT_COMPARABLE`

Verify the actual current vocabulary and meanings.

Do not add new comparison statuses merely to distinguish internal failure causes.

Instead, distinguish three separate layers.

### Layer A — Coverage

Whether the implementation declares a comparison target and has a known extraction/mapping path.

Suggested internal diagnostic categories:

- `TARGET_NOT_DECLARED`
- `MAPPING_NOT_IMPLEMENTED`
- `MAPPING_DECLARED`
- `MAPPING_UNKNOWN`

These are diagnostic labels, not new comparison statuses.

### Layer B — Resolution

Whether the runtime can select and extract the relevant values.

Examples:

- `FILAMENT_IDENTITY_UNRESOLVED`
- `FILAMENT_SLOT_AMBIGUOUS`
- `PLATE_SELECTION_UNRESOLVED`
- `SOURCE_PARAMETER_MISSING`
- `SOURCE_PARAMETER_INVALID`
- `VALUE_NOT_NUMERIC`
- `INHERITANCE_NOT_RESOLVED`

Use the actual supported failure conditions.

Do not invent diagnostics that cannot be grounded in the implementation.

### Layer C — Comparison

Whether resolved values are comparable and whether they match.

Examples:

- `MATCH`
- `MISMATCH`
- `MISSING_IN_PRESET`
- `MISSING_IN_3MF`
- `UNRESOLVED`
- `AMBIGUOUS`
- `NOT_COMPARABLE`

Preserve the existing public status semantics.

**A missing implementation mapping must not be reported as though it were an ordinary user-provided missing value.**

Likewise, an unresolved filament identity must not be described as a parameter mapping defect without evidence.

## 5. Missing-value correctness invariants

The comparison engine must obey the following principles.

### 5.1 No false MATCH

`MATCH` may only be emitted when both required comparison operands have been successfully resolved and compared under the existing comparison rules.

A missing operand must never become `MATCH` through:

- Shared default values.
- Empty strings.
- `None` normalization.
- Missing-key fallbacks.
- Implicit zero conversion.
- Identical placeholder objects.
- Unresolved inheritance.
- A failed lookup silently returning a comparison-compatible value.

Inspect the existing comparison logic carefully.

### 5.2 Preserve missing-side distinction

If the Native Preset operand is absent and the 3MF operand is present, the result must follow the existing `MISSING_IN_PRESET` semantics.

If the 3MF operand is absent and the Native Preset operand is present, the result must follow the existing `MISSING_IN_3MF` semantics.

If both are absent, do not automatically emit `MATCH`.

Determine the intended existing contract for both-absent operands, document it, and test it.

If the current schema cannot represent the condition unambiguously, use the most appropriate existing non-`MATCH` status with a grounded reason.

### 5.3 Distinguish absent from unresolved

A known missing key and a value that cannot be selected because of slot ambiguity are different conditions.

Do not turn ambiguity into missing-value classification.

Do not turn missing-value classification into `UNRESOLVED` without a concrete resolution failure.

### 5.4 No fabricated values

Never synthesize a numeric comparison operand merely to complete a report.

Do not silently fall back to unrelated printer or filament values.

Do not assume the first filament slot is correct.

## 11. Regression test design

Add focused tests at three levels.

### Level 1 — Comparison invariants

Use synthetic operands to verify:

- Equal values produce `MATCH`.
- Unequal values produce `MISMATCH`.
- Missing Native operand is not `MATCH`.
- Missing 3MF operand is not `MATCH`.
- Both missing operands are not `MATCH`.
- Invalid operands are not `MATCH`.
- Ambiguous operands are not `MATCH`.
- Unresolved operands are not `MATCH`.

### Level 2 — Extractor and selector behavior

Use controlled fixtures to verify:

- Valid single-filament identity.
- Valid multi-filament identity selection, where supported.
- Ambiguous filament selection.
- Missing identity metadata.
- Missing parameter keys.
- Invalid numeric values.
- Correct source-path reporting.
- No implicit first-slot fallback.

### Level 3 — End-to-end Consistency

Use committed Native Preset/3MF fixture pairs to verify:

- Correct schema version.
- Correct slicer identity.
- Correct selection status.
- Correct comparison row count.
- Correct summary aggregation.
- Correct missing-value classification.
- Correct mismatch detection.
- No false `MATCH`.

Include at least one negative test where a deliberately changed comparable parameter produces `MISMATCH`, provided a valid resolvable fixture pair exists.

If no such fixture exists, report that limitation rather than fabricating an end-to-end success.
