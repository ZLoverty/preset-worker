# P9-F1 — Photo Patch Update and Evidence Preservation

## Objective

Fix the existing Preset Update workflow so that a partial photo submission does not delete unrelated photo evidence from the master Preset record.

Implement field-level photo patch semantics:

**For each photo field, a newly submitted photo replaces the existing photo. If no new photo is submitted, preserve the existing photo unchanged.**

Each photo field supports at most one effective photo.

Apply this rule consistently to the approved Preset, its version history, and the Submission UI.

This is a narrowly scoped business-logic correction. Do not redesign the photo storage architecture.

---

## 1. Business Rules

### 1.1 Create

For a new Preset:

- Use photos uploaded in the current Submission.
- Preserve existing Create-specific required-photo validation.
- Do not inherit photos from another Preset.
- Each photo field has at most one effective photo.

### 1.2 Update

For an existing Preset:

- If a photo field contains a newly submitted photo, replace that field's existing photo.
- If a photo field is empty or omitted in the current Submission, preserve the existing photo.
- Do not append photos.
- Do not clear unrelated photo fields.
- Do not require all photo fields to be uploaded again.
- Do not interpret an empty photo field as a deletion request.

### 1.3 Rejected submissions

A rejected Submission must not change:

- Master Preset photos.
- Current version photos.
- Published photo projections.

### 1.4 Repeated processing

Reprocessing the same approved Submission must not duplicate photos or cause previously inherited photos to disappear.

Preserve the existing approval idempotency mechanisms.

## 4. Define Field-Level Patch Semantics

Implement a small, deterministic merge function using the existing photo field definitions.

Conceptually:

```python
def merge_photos(existing, submitted, photo_fields):
    merged = dict(existing)

    for field in photo_fields:
        new_photo = submitted.get(field)

        if new_photo:
            merged[field] = new_photo

    return merged
```

Adapt this to the actual Feishu attachment representation.

Requirements:

- Use the existing configured photo fields.
- Preserve unrelated fields.
- Preserve existing attachment metadata where required.
- Do not rely on arbitrary dictionary keys from user input.
- Do not introduce a new photo schema.
- Do not use a new database.

### Empty values

Treat the following as "no new photo" where appropriate to the existing API:

- Missing field.
- `None`.
- Empty attachment array.
- Empty attachment value.

These must not clear an existing photo during Update.

### New values

A non-empty submitted photo field replaces the previous effective value for that field.

Each field should have exactly one effective photo at most.

Inspect how the current UI and Feishu API handle multiple attachments in one field.

If multiple photos are submitted for a single-photo field, apply the existing validation conventions to reject the ambiguous input rather than silently selecting an arbitrary photo.

Do not implement photo append behavior.

### Deletion

Explicit photo deletion is out of scope.

An empty Submission field does not mean delete.

Do not add a delete button or deletion sentinel in this phase.

## 6. PresetVersion Photo Semantics

Preserve two distinct concepts:

**Submission photos** represent what the engineer uploaded in this particular Submission.

**Effective version photos** represent the complete set of photos applicable to the approved Preset version.

For an Update:

- The Submission retains only the newly uploaded photos.
- The new PresetVersion should retain the effective merged photo snapshot, where the current version schema supports photo snapshots.
- The master Preset should project the same effective photo state as the new current version.

Example:

```text
Submission v2:
    Temperature = D
    Flow = empty
    PA = empty

PresetVersion v2:
    Temperature = D
    Flow = B
    PA = C

Preset current:
    Temperature = D
    Flow = B
    PA = C
```

Inspect the existing PresetVersion schema first.

If PresetVersion currently has no photo snapshot storage, do not introduce new Feishu fields automatically.

Instead:

1. Implement the master projection correction using existing fields.
2. Document the version-history limitation.
3. Report whether supporting complete historical photo snapshots requires a separate schema change.

Do not claim historical photo snapshots are preserved if the data model cannot store them.

## 8. Update Miaoda Validation

The UI must distinguish Create from Update.

### Create

Preserve existing required-photo rules.

Do not weaken Create validation.

### Update

Allow photo fields to remain empty.

An engineer should be able to update only Preset parameters without uploading any new photos.

An engineer should also be able to upload only one or a subset of photo types.

The Submit button must not require all photo fields for Update.

### Important

Do not automatically copy old photos into the Submission form's upload fields.

The Submission should represent the current engineer's new evidence, not a reconstructed full photo snapshot.

If the UI already displays existing master photos for reference, preserve that behavior.

Do not represent inherited photos as newly uploaded attachments.

### Operation detection

Reuse the existing authoritative create/update determination.

Do not infer operation solely from whether photo fields are empty.

Do not change operation detection rules as part of this task.

## 9. Preview and Submit Behavior

Do not change the existing native Preset Preview or formal Submit enrichment behavior.

Photo patch semantics apply when an Update is approved and the master Preset projection is updated.

Before approval:

- The master Preset retains its current photos.
- The Submission retains newly uploaded photos only.
- Preview does not modify master photos.
- Formal Submit does not prematurely modify master photos.

After approval:

- The effective photo set is merged.
- The master Preset reflects the new effective set.
- Existing unrelated photos remain unchanged.

Rejected submissions do not modify the master Preset.
